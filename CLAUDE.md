# ClinIQ

AI-assisted clinical trial patient matching for pharma and CROs, with two sides:

- **Clinician/sponsor side** (`/`) — upload a trial protocol, Claude extracts structured
  eligibility criteria, then uploaded patient records are scored against those criteria.
- **Patient side** (`/patient`) — a ClinicalTrials.gov-style "Focus your search" structured
  filter form (condition, location, eligibility, phase, study type, dates, etc. — all
  optional), which directly drives a live search of recruiting trials worldwide on
  ClinicalTrials.gov; Claude then scores/explains how well each real trial fits. This mirrors
  the public tool [trialgpt.app](https://trialgpt.app/) (itself inspired by NIH's TrialGPT
  research, see [Jin et al., Nature Communications 2024](https://www.nature.com/articles/s41467-024-53081-z))
  — search real trial registries → explain eligibility → rank. Not US-only: location is a
  free-text "address, city, state, zip, or country" field and every example/test in this repo
  has confirmed non-US trials surface correctly (e.g. UK, Japan).

## Stack

- `frontend/` — Next.js 16 (App Router, TypeScript, Tailwind v4). Two client-rendered
  wizards sharing `StepIndicator`: clinician flow (protocol → patients → results) at `/`,
  patient flow (search → trials) at `/patient`.
- `backend/` — FastAPI (Python). Endpoints backed by the Anthropic Claude API, plus a live
  integration with the public ClinicalTrials.gov v2 API (no auth required) for the patient
  side.
- Model: `claude-sonnet-4-6` via the `anthropic` Python SDK, called with forced tool use
  (`tool_choice`) so responses are always structured JSON, not free text to parse.

## Running locally

Backend:
```
cd backend
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # fill in ANTHROPIC_API_KEY
uvicorn app.main:app --reload --port 8000
```

Frontend:
```
cd frontend
npm install
cp .env.local.example .env.local   # NEXT_PUBLIC_API_URL=http://localhost:8000
npm run dev
```

## Backend structure

- `app/main.py` — FastAPI app, CORS, router registration, `/api/health`.
- `app/config.py` — env-driven settings (`ANTHROPIC_API_KEY`, `CLAUDE_MODEL`, `CORS_ORIGINS`).
- `app/models/schemas.py` — all Pydantic request/response models shared across endpoints.
- `app/services/claude_client.py` — cached `Anthropic` client singleton.
- `app/services/criteria_parser.py` — `POST /api/parse-criteria` logic. Sends the protocol
  text to Claude with a forced `extract_eligibility_criteria` tool call; splits the result
  into `inclusion_criteria` / `exclusion_criteria`, each with a generated `id`.
- `app/services/patient_matcher.py` — `POST /api/match-patients` logic. For one patient,
  sends the full criteria list + patient record to Claude with a forced
  `submit_patient_assessment` tool call; returns per-criterion status/evidence/confidence
  plus an overall score and eligibility verdict.
- `app/routers/matching.py` — fans the per-patient Claude calls out across a
  `ThreadPoolExecutor` (max 5 concurrent) so multiple patients are scored in parallel.

Criterion IDs generated by `criteria_parser` (`inc-<n>-<hex>` / `exc-<n>-<hex>`) are the
join key between the criteria response and each patient's `criterion_assessments` — the
frontend never recomputes them.

### Patient side (`/api/patient/find-trials`)

- `app/models/schemas.py:TrialSearchFilters` — the full structured form: basic search
  (condition/other terms/intervention/location/title), study status, eligibility (sex, age
  groups or manual range, healthy volunteers), phase, study type (+ expanded access
  subtypes), results, documents, funder type, and six date-range pairs. Every field here is
  real and wired to an actual ClinicalTrials.gov filter — nothing in this form is decorative.
- `app/services/ctgov_client.py` — calls `https://clinicaltrials.gov/api/v2/studies` (public,
  no API key). `_build_advanced_filter()` translates most of `TrialSearchFilters` into a
  single Essie `filter.advanced` expression (e.g. `AREA[Sex](FEMALE OR ALL) AND
  AREA[Phase](PHASE2 OR PHASE3)`); basic fields map to `query.cond`/`query.term`/`query.intr`/
  `query.locn`/`query.titles`. Field/enum names (`Sex`, `Phase`, `StudyType`,
  `LeadSponsorClass`, `LargeDocHasProtocol`, etc.) were confirmed against the live
  `/studies/metadata` and `/studies/enums` endpoints, not guessed. "With/without results" uses
  the `AREA[ResultsFirstPostDate]RANGE[MIN,MAX]` exists-trick (matches CT.gov's own advanced
  search behavior). Age is the one filter applied client-side after fetching (`_passes_age_filter`)
  rather than via Essie, since correctly overlapping a patient's age-bucket against each
  trial's `[minimumAge, maximumAge]` range is simpler and more reliably correct in Python than
  in Essie.
- `app/services/trial_matcher.py` — `_build_patient_context()` turns the non-search fields
  (condition, sex, age, healthy-volunteer flag, and the optional free-text
  `additional_details`) into a short text block, which along with one trial's raw
  `eligibilityCriteria` text goes to Claude (forced `assess_trial_fit` tool call). Returns a
  patient-friendly `eligibility` verdict, `score`, plain-language `explanation`, and a few
  `key_points` tagged supporting/conflicting/missing. Because the structured form alone is
  often thin on clinical detail, `insufficient_info`/`possibly_eligible` verdicts are common
  and expected, not bugs — `additional_details` is the escape hatch for patients who want a
  more confident verdict.
- `app/routers/patient.py` — `find-trials` does retrieval (CT.gov search, capped by
  `max_results`) then matching (parallel `ThreadPoolExecutor`, same pattern as
  `matching.py`), then sorts by score descending. This is the same
  retrieve-then-match-then-rank shape as the real TrialGPT paper, just collapsed into one
  Claude call per trial instead of TrialGPT's separate retrieval/matching/ranking models.

This only searches ClinicalTrials.gov — it does not cover CTIS (the EU trials registry) the
way the real trialgpt.app does.

## Frontend structure

- `src/app/page.tsx` — top-level wizard state machine (`step` 0/1/2) and API call
  orchestration. No global state library; everything lives here and is passed down as props.
- `src/components/ProtocolStep.tsx` — protocol text input (paste or `.txt` drop) + trial ID.
- `src/components/PatientStep.tsx` — criteria review (via `CriteriaList`) + patient record
  intake (multi-file drop, one file per patient, or manual paste).
- `src/components/ResultsStep.tsx` — ranked, expandable per-patient results with
  criterion-level evidence.
- `src/lib/api.ts` — thin fetch wrapper around the two backend endpoints; reads
  `NEXT_PUBLIC_API_URL`.
- `src/lib/types.ts` — TypeScript types mirroring `backend/app/models/schemas.py` exactly.
  Keep these in sync by hand when the Pydantic models change.
- `src/app/patient/page.tsx` — patient-side wizard (search → trials), same
  state-in-page-component pattern as `src/app/page.tsx`. `src/components/patient/SearchFiltersStep.tsx`
  is the big CT.gov-style form (`TrialSearchFilters` in, lifted to the page); collapsible
  "More filters" / "More ways to search" sections default closed, matching the real site.
  `StepIndicator` takes an optional `steps` prop so both wizards can reuse it with their own
  labels.

## Conventions

- Backend targets Python 3.9 syntax: use `typing.Optional[...]`, not `X | None`, in any
  context evaluated at runtime (function signatures, etc.). `list[X]`/`dict[X, Y]` subscript
  generics are fine (PEP 585, available since 3.9).
- Claude calls always use `tool_choice={"type": "tool", "name": ...}` with a single tool
  definition — this is the structured-output pattern for this codebase. Don't switch to
  prompting for raw JSON.
- Patient records and protocol text are expected to already be de-identified before they
  reach this app; the app does not perform PHI scrubbing itself.
- No database yet — everything is request/response, state lives only in the frontend's
  React state for the duration of one session.

## Known gaps / not yet built

- No auth, no persistence, no PDF parsing — protocol and patient inputs are plain text only.
- No automated test suite yet.
- Patient side only searches ClinicalTrials.gov (no CTIS/EU registry).
- No medical disclaimer gating/consent flow beyond the static text on the patient pages —
  worth revisiting before any real patient-facing deployment.
